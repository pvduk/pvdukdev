O Navegador: o cache que você controla

Memory cache, HTTP cache e Service Worker — as três camadas que decidem a latência que o seu usuário sente.

Cache não é uma feature. É uma arquitetura.

Toda requisição que o seu usuário faz é, na verdade, uma pergunta em cadeia: "você tem esse dado?". Cada camada responde "sim" o mais rápido que pode — mesmo que a resposta esteja levemente desatualizada. A essa mentira autorizada damos o nome de cache hit.

Nesta série, vamos percorrer o pipeline completo, do clique ao spin do disco. Começamos pelo lugar onde você, engenheiro frontend, tem mais poder: o navegador.

As três frentes de cache do browser

1. Memory Cache (RAM)

Extremamente rápido, volátil. Armazena recursos já parseados — CSS, JS, imagens decodificadas — durante a sessão da aba. Morre quando a aba fecha. É o cache que faz a navegação entre páginas do mesmo site parecer instantânea.

2. Disk Cache (HTTP Cache)

Persistente entre sessões. É aqui que vivem as duas decisões mais importantes que você toma como frontend:

  • Cache-Control decide POR QUANTO TEMPO o recurso é fresco. max-age=3600 significa: "por uma hora, nem pergunte ao servidor".
  • ETag decide COMO VALIDAR. Quando o recurso envelhece, o browser não baixa de novo: ele pergunta "ainda é o mesmo?" via If-None-Match. Se for, o servidor responde 304 Not Modified — zero bytes de corpo.
Insight: um 304 bem configurado é a otimização mais barata que existe. Você não reduziu requests; você reduziu payload a quase zero.

3. Service Worker + Cache API

O proxy programável (especificação da WHATWG). Com ele, o browser ganha uma camada que VOCÊ controla por código: interceptar a requisição antes dela sair, decidir servir do cache, da rede, ou dos dois (padrões como Cache First e Stale-While-Revalidate).

Insight: com Service Worker, o Cache-Control deixa de ser o único rei. Você pode servir a página inteira offline — ou mentir com elegância enquanto revalida em background.

A camada que ninguém lembra: navegação

bfcache (back/forward cache): o browser guarda a página INTEIRA — DOM, JS, estado — ao navegar para outra. Voltar não é um request; é um restore. Milissegundos.

E os hints de recurso: preconnect antecipa o handshake de conexões, preload baixa recursos críticos antes do HTML pedir. São cache de futuro: você prepara o terreno antes da requisição existir.

Early Hints (HTTP 103) e HTTP/3/QUIC estão reduzindo ainda mais o custo do "primeiro contato". Mas isso é conversa da Parte 2 — a borda.

Mão na massa: Implementação e Teste Automatizado

Teoria sem código vira dogma. Vamos materializar o conceito de Memory Cache com TTL e fallback de rede em uma função utilitária pura de 15 linhas — e escrever o teste unitário usando o test runner nativo do Node.js (node:test), sem nenhuma dependência de terceiros.

1. O Utilitário de Cache em Memória

A função recebe uma URL, uma função fetch injetável (para facilitar mocks e testes), um store de cache e um tempo de vida (TTL): 

/**
 * Busca recurso com cache em memória e expiração TTL.
 * @param {string} url - Endpoint a consultar
 * @param {Function} fetcher - Função fetch (injetável para testes)
 * @param {Map} cacheStore - Store em memória
 * @param {number} ttlMs - Tempo de vida em milissegundos
 */
export async function fetchWithMemoryCache(url, fetcher = fetch, cacheStore = new Map(), ttlMs = 60000) {
  const now = Date.now();
  const cached = cacheStore.get(url);

  // Cache Hit: Dado fresco na memória RAM
  if (cached && (now - cached.timestamp < ttlMs)) {
    return { data: cached.data, fromCache: true };
  }

  // Cache Miss: Busca na rede e armazena na memória
  const response = await fetcher(url);
  const data = await response.json();
  cacheStore.set(url, { data, timestamp: now });

  return { data, fromCache: false };
}

2. O Teste Unitário Automatizado (TDD / BDD)

Validamos os dois comportamentos fundamentais: no primeiro acesso (miss), a rede é requisitada; no segundo acesso (hit), a resposta é instantânea e a rede é poupada com zero latência. 

// cache-helper.test.js
import test from 'node:test';
import assert from 'node:assert';
import { fetchWithMemoryCache } from './cache-helper.js';

test('Pipeline de Cache: deve alternar entre Cache Miss e Cache Hit', async () => {
  let networkRequests = 0;
  const mockFetcher = async () => {
    networkRequests++;
    return { json: async () => ({ status: 'success', version: 1 }) };
  };
  const cache = new Map();

  // 1º Acesso: Cache Miss (deve chamar a rede)
  const first = await fetchWithMemoryCache('/api/config', mockFetcher, cache, 5000);
  assert.strictEqual(first.fromCache, false, 'Primeira chamada deve ser cache miss');
  assert.strictEqual(networkRequests, 1, 'Deve ter disparado exatamente 1 requisição na rede');
  assert.deepStrictEqual(first.data, { status: 'success', version: 1 });

  // 2º Acesso: Cache Hit (deve servir da memória RAM sem nova requisição)
  const second = await fetchWithMemoryCache('/api/config', mockFetcher, cache, 5000);
  assert.strictEqual(second.fromCache, true, 'Segunda chamada deve ser cache hit');
  assert.strictEqual(networkRequests, 1, 'Não deve incrementar requisições na rede');
  assert.deepStrictEqual(second.data, { status: 'success', version: 1 });
});
Por que testar assim? Injetar o fetcher e o cacheStore torna a arquitetura 100% desacoplada e testável em milissegundos sem precisar subir servidores ou emuladores pesados.

TL;DR

  • Memory cache: rápido, volátil, vive na sessão da aba.
  • Disk cache: Cache-Control define o prazo de validade; ETag valida com 304.
  • Service Worker: cache programável; você decide a política por código.
  • bfcache + hints: a navegação também tem cache — e quase ninguém usa direito.

O browser respondeu "não tenho". A requisição agora sai da sua máquina. Na Parte 2, ela atravessa DNS, TLS e chega à camada mais quente da engenharia moderna: a borda.
