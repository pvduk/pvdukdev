A Anatomia do Cache, Parte 1: O Navegador

Memory cache, HTTP cache e Service Worker — as três camadas que decidem a latência que o seu usuário sente.

Série: A Anatomia do Cache · Parte 1 de 4 30 de Agosto de 2026 12 min de leitura
  • #cache
  • #performance

Paulo Dukven Engenheiro de Software e FullStack C#/React

Cache não é uma feature. É uma arquitetura.

Toda requisição que o seu usuário faz é, na verdade, uma pergunta em cadeia: "você tem esse dado?". Cada camada responde "sim" o mais rápido que pode — mesmo que a resposta esteja levemente desatualizada. A essa mentira autorizada damos o nome de cache hit.

Nesta série, vamos percorrer o pipeline completo, do clique ao spin do disco. Começamos pelo lugar onde você, engenheiro frontend, tem mais poder: o navegador.

As três frentes de cache do browser

1. Memory Cache (RAM)

Extremamente rápido, volátil. Armazena recursos já parseados — CSS, JS, imagens decodificadas — durante a sessão da aba. Morre quando a aba fecha. É o cache que faz a navegação entre páginas do mesmo site parecer instantânea.

2. Disk Cache (HTTP Cache)

Persistente entre sessões. É aqui que vivem as duas decisões mais importantes que você toma como frontend:

  • Cache-Control decide POR QUANTO TEMPO o recurso é fresco. max-age=3600 significa: "por uma hora, nem pergunte ao servidor".
  • ETag decide COMO VALIDAR. Quando o recurso envelhece, o browser não baixa de novo: ele pergunta "ainda é o mesmo?" via If-None-Match. Se for, o servidor responde 304 Not Modified — zero bytes de corpo.
Insight de Arquitetura

Um 304 bem configurado é a otimização mais barata que existe. Você não reduziu requests; você reduziu payload a quase zero.

3. Service Worker + Cache API

O proxy programável (especificação da WHATWG). Com ele, o browser ganha uma camada que VOCÊ controla por código: interceptar a requisição antes dela sair, decidir servir do cache, da rede, ou dos dois (padrões como Cache First e Stale-While-Revalidate).

Controle Absoluto de Camadas

Com Service Worker, o Cache-Control deixa de ser o único rei. Você pode servir a página inteira offline — ou mentir com elegância enquanto revalida em background.

A camada que ninguém lembra: navegação

bfcache (back/forward cache): o browser guarda a página INTEIRA — DOM, JS, estado — ao navegar para outra. Voltar não é um request; é um restore. Milissegundos.

E os hints de recurso: preconnect antecipa o handshake de conexões, preload baixa recursos críticos antes do HTML pedir. São cache de futuro: você prepara o terreno antes da requisição existir.

Otimização Contínua

Early Hints (HTTP 103) e HTTP/3/QUIC estão reduzindo ainda mais o custo do "primeiro contato". Mas isso é conversa da Parte 2 — a borda.

Mão na massa

Chega de teoria. Se você não vê o cache funcionando na tela, vira religião. Vamos pegar o conceito abstrato de Memory Cache com TTL e transformar em um script que você copia, cola no OneCompiler e vê acontecer na sua frente. Sem Docker, sem subir container, sem reza pro CI passar.

1. O utilitário que resolve

Repara que não tem framework aqui. Não tem biblioteca de cache de 2MB, não tem Redis, não tem enterprise solution. É um Map, uma subtração de timestamp e uma função fetch injetável. É assim que a maioria dos caches de produção começa — antes de alguém decidir que "precisava" de mais uma dependência. 


const { performance } = require('perf_hooks');

// 1. O Utilitário de Cache em Memória
async function fetchWithMemoryCache(url, fetcher, cacheStore, ttlMs) {
  const now = Date.now();
  const cached = cacheStore.get(url);

  // Cache Hit: Dado fresco na memória RAM
  if (cached && (now - cached.timestamp < ttlMs)) {
    return { data: cached.data, fromCache: true };
  }

  // Cache Miss: Busca na rede e armazena na memória
  const response = await fetcher(url);
  const data = await response.json();
  cacheStore.set(url, { data, timestamp: now });

  return { data, fromCache: false };
}

// --- Simulação Prática da Latência de Rede ---
// Em ambientes offline (sandboxes de compiladores online), simulamos o custo real da rede.
const sleep = (ms) => new Promise(resolve => setTimeout(resolve, ms));

async function runCacheTest() {
  const LATENCIA_REDE_MS = 2000; // 2 segundos de "ida e volta" no servidor
  
  let networkRequests = 0;
  const mockFetcher = async (url) => {
    networkRequests++;
    await sleep(LATENCIA_REDE_MS); // O "custo" da rede
    return { json: async () => ({ status: 'success', version: 1 }) };
  };

  const cache = new Map();
  const url = '/api/config';

  console.log("INICIANDO PIPELINE DE CACHE...\n");

  // --- 1º ACESSO (CACHE MISS) ---
  console.log(`[1/2] Buscando ${url} (Indo até o servidor)...`);
  const startMiss = performance.now();
  
  const first = await fetchWithMemoryCache(url, mockFetcher, cache, 5000);
  
  const endMiss = performance.now();
  const timeMiss = (endMiss - startMiss).toFixed(2);
  
  console.log(`Retornou do Cache? ${first.fromCache ? 'Sim' : 'Não (Veio da Rede)'}\n`);


  // --- 2º ACESSO (CACHE HIT) ---
  console.log(`[2/2] Buscando ${url} novamente (O Cache vai agir?)...`);
  const startHit = performance.now();
  
  const second = await fetchWithMemoryCache(url, mockFetcher, cache, 5000);
  
  const endHit = performance.now();
  const timeHit = (endHit - startHit).toFixed(2);
  
  console.log(`Retornou do Cache? ${second.fromCache ? 'Sim (Veio da RAM)' : 'Não'}\n`);


  // --- O "SOCO" VISUAL NO CONSOLE ---
  console.log("=".repeat(45));
  console.log("📊 RELATÓRIO DE LATÊNCIA:");
  console.log(`1ª Chamada (Rede):  ${timeMiss} ms`);
  console.log(`2ª Chamada (Cache): ${timeHit} ms`);
  console.log(`Economia de tempo:  ${((timeMiss / timeHit) || 0).toFixed(0)}x mais rápido!`);
  console.log(`Requisições poupadas: ${networkRequests === 1 ? 'SIM (A rede não foi chamada na 2ª vez)' : 'NÃO'}`);
  console.log("=".repeat(45));
}

runCacheTest();

2. A prova no terminal

Quando você apertar Run, o console vai literalmente travar por 2 segundos na primeira chamada. Você vai sentir a latência na pele — é exatamente assim que o seu usuário se sente quando o cache falha e o front é obrigado a esperar o backend processar a mesma query de novo.

Aí vem a segunda chamada e o tempo pisca em 0.05ms. É nesse momento que a teoria vira arquitetura: você eliminou a ida e volta no servidor, poupou o banco de dados e entregou a tela antes do usuário piscar.

Por que o performance.now() e não o Date.now()? Date.now() tem precisão de milissegundo inteiro. performance.now() mede em microssegundos. Quando você está comparando 2000ms contra 0.05ms, essa diferença de precisão é o que separa uma medição honesta de um número redondo que esconde a realidade.

Regras de bolso

  • Memory cache: instantâneo, some quando fecha a aba. Usa pra transição de tela em SPA, onde o usuário nem percebe que teve round-trip.
  • Disk cache: aqui mora o perigo. Cache-Control define validade, ETag define como validar. Um 304 Not Modified bem feito é a otimização mais barata que existe — zero bytes trafegados.
  • Service Worker: é quando você para de confiar só no header e começa a mandar no cache por código. Dá pra servir offline, dá pra mentir elegante enquanto revalida em background.
  • bfcache e hints: o browser guarda a página inteira quando você navega pra fora. Voltar não é request, é restore. Economiza centenas de ms e você nem escreveu uma linha.

O browser respondeu "não tenho". A requisição agora sai da sua máquina. Na Parte 2, ela atravessa DNS, TLS e chega à camada mais quente da engenharia moderna: a borda.
